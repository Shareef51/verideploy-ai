# OpenAI Image-Intelligence Layer

## Purpose

Image Intelligence Layer turns the Multimodal Sequence image intake and Responses API Adapter Responses transport into a production image-understanding boundary. It does not implement visual retrieval (Visual Document Retrieval), multimodal RAG fusion (Multimodal RAG Fusion), or the autonomous VisualEvidenceAgent (Visual Evidence Agent).

## Runtime flow

```text
Multimodal Sequence admitted image/object
 -> multimodal worker / trusted private caller
 -> SecureImagePreparer
 - decode by content
 - reject unsupported/animated/oversized images
 - EXIF orientation normalization
 - metadata stripping via decode/re-encode
 - SHA-256 provenance
 - detail policy
 -> ImageIntelligenceService
 - untrusted-image instruction boundary
 - AIRequest with input_text + input_image
 -> Model Routing Cost Policy router / cost / concurrency
 -> Responses API Adapter OpenAI Responses adapter
 -> validated dashboard / architecture / error-screen result
 -> provenance + observation/inference graph
```

## Security boundary

Image Intelligence Layer does not fetch arbitrary image URLs. The internal request accepts bytes already retrieved from an authorized object-storage path and sends the sanitized image to OpenAI as a data URL. This prevents the image layer from becoming an SSRF-capable remote fetcher.

The image is decoded and re-encoded before model submission. Application metadata and image metadata are not forwarded blindly. The prepared object receives a new content hash while retaining the original content hash for lineage.

## Detail policy

Supported logical detail values are `low`, `high`, `original`, and `auto`. The default is `auto`. Dense dashboards and architecture images are promoted to `high`; error screens use `high`. `original` must be explicitly enabled by policy because model support and cost/latency trade-offs vary.

Configuration:

```text
AI_IMAGE_DEFAULT_DETAIL=auto
AI_IMAGE_ALLOW_ORIGINAL_DETAIL=false
AI_IMAGE_MAX_PIXELS=40000000
AI_IMAGE_MAX_SIDE=8192
```

## Observation versus inference

Direct visual statements are represented by `VisualObservation`. Each observation must contain the exact `image_id`, confidence, and optional normalized locator. Numeric claims require an uncertainty qualifier.

Interpretations are represented separately by `VisualInference`. Every inference must cite one or more valid observation IDs. A result containing a fabricated observation reference is rejected before it can enter business logic.

## Task-specific schemas

- `DashboardAnalysisResult` adds evidence-backed anomaly records.
- `ArchitectureAnalysisResult` adds observed components and relationships.
- `ErrorScreenAnalysisResult` adds visible error signals.

All three inherit the same immutable provenance and observation/inference validation rules.

## Prompt-injection handling

The system prompt content generated by the image service states that all text visible in the image is untrusted data. Instructions, credential requests, and tool directives embedded in screenshots or diagrams are not executable instructions.

## Known Image Intelligence Layer boundary

Image Intelligence Layer validates model JSON with Pydantic after generation. The reusable JSON-Schema/structured-output repair platform is intentionally deferred to Structured Output Platform. Visual retrieval, cross-image retrieval ranking, PDF page retrieval, audio/video fusion, and VisualEvidenceAgent behavior remain future milestones.
